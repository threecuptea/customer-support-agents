### How human-in-the-loop work in LangGraph's interrupt - Command resume framework
When human-in-the-loop step is needed, issue `interrupt` with key-value dictionary of info to convey to the frontend like actions (action buttons), and message. LangGraph captures state in StateSnapshot including all accumulated messages (HumanMessage, AIMessage and ToolMessage).  Each message comes with argument details and checkpoint_id. In LangGraph, you can invoke a config with thread_id and checkpoint_id, it will execute/ resume the worklfow of that thread at that checkpoint_id. That's how you can test partial workflow in LangGraph. `interrupt` will release the thread.  When a human press a button, API will issue a Command(resume=...). Langugraph will resume the workflow at the point following `interrupt`.  It's important that `interrupt` need to be at the very beginning of that node.  Any preparation should be in a separate node.

**We implememented Langgraph interrupt - Command resume framework in Approval workflow used by CSR to draft an email by LLM.** The CSR can choose `approve/ edit/ reject`. Edit will do a minor modification on the content.  Reject will give the feedback and ask for re-draft. It is blocking the thread until the requester press any of those buttons.  

### We will implement human-in-the-loop in the manual approve/ reject/ flag return/ refund business workflow. However, we won't use LangGraph's interrupt - Command/ resume fraemwork.
The customer will receive a confirmation email instead.  It's asynchronous and non-blocking in terms of system design.  It's blocking from the business perspective.  A return/ refund request won't move forward until a CSR review it.

**Why do I decide not to use Langgraph interrupt - Command resume in return/ refund processing?**
Once a thread is in `interrupted` state, we need to invoke with Command/ resume in order for the graph to operate normally.  If the app accidentally invoke the graph without Command/ resume, Langraph will issue a fresh `interrupt`. Yes, it will `re-interrupt`.  That might lead to a unknown consequence. Customer-support-agent is an interactive app with multiple endpoints.  We shouldn't block the customer from using the app after the interrupt. Then, we have to check if the thread is in `interrupted` state and invoke with Command/ resume for all endoints if it is.  Doing so will unblock the graph and defeat the purpose which is blocking!!

Langgraph interrupt - Command resume framework work well if the person to request LLM's action is also the person to review it like CSR asking LLM tp draft an email.  That works just like chatting. However, Langgraph interrupt - Command will affect the customer/user interaction in this case and does not reach its goal.  That's my concern.


### Key files

### Routing guard

The single-container image serves both the API and the Next.js static export (`frontend/out`) from one FastAPI app (`backend/main.py`):

- All API routes are registered under `/api/*` and are added to the router before the catch-all, so they always match first.
- `/_next` is mounted via `StaticFiles` (guarded by an `is_dir()` check, since `frontend/out` won't exist when running the backend standalone in dev).
- A catch-all `GET /{full_path:path}`, registered last, serves the rest of `frontend/out`: it 404s immediately if `full_path` starts with `api/` (explicit guard, on top of registration order already protecting this), then tries the exact file, `{full_path}.html`, `{full_path}/index.html`, and — only for the empty path (`/`) — `index.html`. Any other unmatched path falls through to the export's own `404.html` (status 404), so typos/dead links don't silently render the homepage with a 200.
- Path traversal is blocked by resolving each candidate and checking `candidate.is_relative_to(FRONTEND_DIR)` before serving it.

### Sqlite persistence paths

`CHECKPOINT_DB` and `STORE_DB` (used in demo mode for durable `AsyncSqliteSaver`/`AsyncSqliteStore`) are configured as relative filenames, but `sqlite3`/`aiosqlite` resolve relative paths against the process's **current working directory at connect time** — not against `.env`'s or `main.py`'s location. Launching `uvicorn`/`pytest` from `backend/` vs. the repo root used to produce sqlite files in different places for the exact same `.env` (and `STORE_DB` needed a `../data/` prefix hack just to land next to `CHECKPOINT_DB` at all).

Fixed by anchoring both at `DATA_DIR = BACKEND_DIR.parent / "data"` in `main.py` (`BACKEND_DIR = Path(__file__).resolve().parent`), via a `_resolve_db_path()` helper:
- A relative filename (e.g. `checkpoints.sqlite`) always resolves under `DATA_DIR` — the repo root's `data/` locally, `/app/data` in the container (Docker's `WORKDIR` puts `main.py` at `/app/backend`, so `BACKEND_DIR.parent` is `/app`), matching the `./data:/app/data` volume mount in `docker-compose.yml`.
- An absolute path is used as-is (an operator override).

`.env`/`.env.example` now just use bare filenames (`checkpoints.sqlite`, `stores.sqlite`); leaving both unset still falls back to in-memory `MemorySaver`/`InMemoryStore` as before.

### Summarize and store in long-terms memory
I did some research on wheather we should summarize messages, store in the long-term and prune messages. Yes, whatever I implement in `summarize_node` (originated from https://pub.towardsai.net/your-first-real-langgraph-project-ac5eb00f923a) is what LangGraph recommends. In `summarize_node`, RemoveMessag mean to delete `messages` in `CustomerSupportState` not `messages` in `StateSnapshot`.  However, judging from `test_general_support_thread_accumulates_and_summarizes` unit test, it also prune `messages` in `StateSnapshot`. What is going on?  Yes, CustomerSupportState store all variables, including `messages` under `values` in `StateSnapshot`. It's the same memory space. Pruning `messages` in `CustomerSupportState` is the same as removing `messages` under `values` in `StateSnapshot`.  That's core knowledge of LangGraph/ LangChain just as knowing how to resume the state of a thread.

Removing "give this answer every time it is asked" and narrowing the situation's scope were the key changes.

### Current API Endpoints
- `GET /api/health` — liveness check
- `POST /api/approval/start` — draft content for a task, pauses for human review (HITL interrupt)
- `POST /api/approval/decide` — resume the approval workflow with `approve` / `edit` / `reject`
- `POST/api/auth` - authorize role: `csr` (customer-support representative) or `customer`.  Users of different role access different screen
- `POST /api/support/general` — general/others FAQ inquiry (fuzzy/LLM match, escalate on low confidence); optional `thread_id` in the request/response resumes the same LangGraph thread across rounds
- `POST /api/support/order/init` - initialize order inquiry by passing in `order_number_provided` from UI and the backend retrieve the `target_order` and start the `order_inquery` conversation
- `POST /api/support/order/continue` - UI calls this endpoint after the customer starts his/ her `order_inquery` and the endpoint can be called multiple time for each new input from the customer
- `POST /api/support/exchange_return/recommend` - take the survey of the customer's choice why he/ she want to exchange/ return and give recommendation and the instruction what's the next step; the response includes `special_exchange_handling` (True for damaged/defective/wrong item, which the UI must not route into the normal return/refund flow)
- `POST /api/support/return_refund/init` - take item(s) to return to put together a RefundRequest and generate ReturnRefundInitialDecision with OrderRefundStatus enum that can be mapped to status of RefundRequest when processing 
- `POST /api/support/return_refund/process` - take ReturnRefundInitialDecision plus `request_human_review_return_refund` into consideration when processing the RefundRequest
- `POST /api/support/return_refund/chat` - engage conversation with the customer for his/ her RefundRequest and set `request_human_review_return_refund` flag upon his/ her request
- `POST /api/support/exit` - UI calls this end when the customer press `Exit` button 
- `GET /{full_path:path}` — catch-all serving the Next.js static export (`frontend/out`); see [Routing guard](#routing-guard)
